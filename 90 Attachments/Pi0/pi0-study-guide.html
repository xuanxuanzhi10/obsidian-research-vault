01

为什么从 VLM 出发——π₀ 的核心直觉

π₀ 的出发点不是"从头训练一个机器人模型"，而是"把已有的视觉语言能力借过来"。

π₀ 的核心直觉来自一个类比：大语言模型（LLM）的成功经验告诉我们，先在海量互联网数据上预训练一个通用模型，再在高质量数据上微调，比从头在小数据上训练效果好得多。π₀ 把这个范式搬到了机器人领域。

为什么不从头训练？

机器人数据很贵——需要真实硬件采集，每小时数据都要人操作。π₀ 的全部训练数据约 10,000 小时，听起来很多，但对比 LLM 动辄几万亿 token 的预训练规模，这只是沧海一粟。如果只用这些数据从头训练一个模型，它永远学不会"红色杯子""放到旁边"这些语义概念。

解决方案：站在 VLM 的肩膀上。用一个已经在互联网规模图文数据上预训练好的视觉语言模型（PaliGemma）作为骨干，它已经理解了图像内容和语言指令的对应关系。π₀ 只需要教它一件新事情：输出连续的机器人动作。

π₀ 的整体架构一句话总结

π₀ = PaliGemma (3B VLM) + 动作专家 (300M) + Flow Matching
VLM 负责"看懂图、理解指令"，动作专家负责"生成精细动作"，Flow Matching 负责"让动作输出是连续的、多模态的分布"。

# π₀ 的工作流程伪代码
def pi0_inference(images, language_cmd, robot_state):
    # 1. VLM 骨干处理视觉和语言
    img_tokens = SigLIP_encoder(images)          # 图像 → token
    lang_tokens = Gemma_tokenizer(language_cmd)   # 文字 → token
    state_token = linear_proj(robot_state)        # 状态 → token

    # 2. 动作专家处理噪声动作
    noise = sample_gaussian(action_dim * H)       # 随机噪声
    action_tokens = action_embed(noise, tau=0)    # 嵌入噪声 + 时间步

    # 3. 两个专家在同一个 Transformer 里交互
    output = transformer(img_tokens, lang_tokens,
                         state_token, action_tokens)

    # 4. 迭代去噪 10 步，得到最终动作
    for step in range(10):
        velocity = action_expert_head(output)
        actions = actions + 0.1 * velocity        # 欧拉积分
        # 重新前向（只需重算动作部分，KV cache 加速）

    return actions  # H=50 步的连续动作块
→ 衔接问题：我们说要"站在 VLM 的肩膀上"，那 π₀ 选了哪个 VLM？它有什么特点？下一节介绍 PaliGemma 骨干。
02

PaliGemma 骨干——继承互联网级视觉语言能力

选择 PaliGemma 不是随意的——它在体积和能力之间取得了最佳平衡。

π₀ 选用 PaliGemma 作为 VLM 骨干。PaliGemma 是 Google 开源的 3B 参数视觉语言模型，采用经典的 Late Fusion（晚融合）架构：先用独立的图像编码器把图片变成 token，再和语言 token 一起送进语言模型的 decoder。

PaliGemma 的两个核心组件

SigLIP 图像编码器（400M 参数）——这是一个 ViT（Vision Transformer），在互联网规模的图文对上用对比学习（Sigmoid Loss）预训练。它把每张图片切成 patch，编码成一系列 token，每个 token 代表图片的一个局部区域。π₀ 用 2-3 个相机拍摄，所以每个观测有 2-3 张图片，各自独立通过 SigLIP 编码。

Gemma 2B 语言模型——这是一个 decoder-only Transformer，是 PaliGemma 的"大脑"。图像 token 经过线性投影层映射到和语言 token 相同的维度后，和语言 token 拼接在一起，送进这个 decoder。Gemma 2B 的具体配置：

参数值含义
width2048每个 token 的特征维度
depth18 层Transformer 层数
mlp_dim16,384FFN 的中间维度（4× width）
num_heads18注意力头数
num_kv_heads1KV 头数（Multi-Query Attention）
head_dim256每个注意力头的维度

Late Fusion 的工作方式

# PaliGemma 的 Late Fusion 流程
def paligemma_forward(images, text):
    # 图像编码（独立的 ViT，不和文字交互）
    for img in images:
        patches = split_into_patches(img, patch_size=14)
        img_tokens = SigLIP_ViT(patches)  # 每张图 → 一串 token

    # 语言编码
    lang_tokens = token_embedding(tokenize(text))

    # Late Fusion：图像 token 投影到语言空间，然后拼接
    img_projected = linear_projection(img_tokens)  # 映射维度
    all_tokens = concat(img_projected, lang_tokens) # 拼在一起

    # 送进 Gemma decoder（因果注意力）
    output = gemma_decoder(all_tokens)
    return output

为什么是 Multi-Query Attention？

num_kv_heads=1 意味着所有 18 个注意力头共享同一组 K 和 V，只有 Q 是各自独立的。这大幅减少了 KV Cache 的显存占用（只需缓存 1 组而不是 18 组 K/V），对推理速度至关重要——后面会看到 π₀ 在推理时要做 10 次去噪前向传播。

为什么选 PaliGemma 而不是更大的模型？

π₀ 论文明确说了：选 PaliGemma "for convenience and because of its comparatively small size (which is useful for real-time control)"。机器人控制需要 实时推理，50Hz 控制频率意味着每 20ms 就要出一次动作。3B 参数是一个在"足够聪明"和"足够快"之间的甜蜜点。当然，论文也说框架兼容任何 VLM——换成更大的模型理论上效果更好，只是推理更慢。

→ 衔接问题：PaliGemma 已经能看懂图和理解指令了，但它不会输出机器人动作。我们不能直接用 PaliGemma 的 decoder 来生成动作吗？答案是可以但效果不好。下一节解释为什么需要一个独立的"动作专家"。
03

动作专家——用更小的参数专门处理机器人模态

π₀ 的关键创新之一：在同一个 Transformer 内部，运行两套独立的权重。

π₀ 的做法灵感来自 Transfusion（一个同时生成文本和图像的模型）：在同一个 Transformer 里，不同类型的 token 走不同的权重。具体来说：

Token 类型走哪套权重参数量维度
图像 token（SigLIP 输出）VLM 专家（PaliGemma）~2.6Bwidth=2048
语言 tokenVLM 专家（PaliGemma）（同上）width=2048
机器人状态 token动作专家（新增）~300Mwidth=1024
噪声动作 token动作专家（新增）（同上）width=1024

"两个专家"怎么在一个 Transformer 里共存？

理解这个设计，关键是理解 Gemma 用的是 Multi-Query Attention（只有 1 个 KV head）。在自注意力层，两套权重只通过注意力机制交互：

# 伪代码：π₀ 一个 Transformer 层的运算
def pi0_layer(img_lang_tokens, state_action_tokens, layer_idx):
    # ========== 自注意力（唯一的交互点）==========
    # VLM 专家算自己的 Q/K/V
    Q_vlm = W_q_vlm[layer_idx](img_lang_tokens)   # [n_vlm, 18, 256]
    K_vlm = W_k_vlm[layer_idx](img_lang_tokens)   # [n_vlm,  1, 256]
    V_vlm = W_v_vlm[layer_idx](img_lang_tokens)   # [n_vlm,  1, 256]

    # 动作专家算自己的 Q/K/V（注意维度更小）
    Q_act = W_q_act[layer_idx](state_action_tokens) # [n_act, 18, 256]
    K_act = W_k_act[layer_idx](state_action_tokens) # [n_act,  1, 256]
    V_act = W_v_act[layer_idx](state_action_tokens) # [n_act,  1, 256]

    # 拼在一起做联合注意力（应用块间因果掩码）
    Q = concat(Q_vlm, Q_act)
    K = concat(K_vlm, K_act)
    V = concat(V_vlm, V_act)
    attn_out = masked_attention(Q, K, V, mask=block_causal)

    # ========== FFN（完全独立，不交互）==========
    vlm_out  = FFN_vlm[layer_idx](attn_out[:n_vlm])    # mlp_dim=16384
    act_out  = FFN_act[layer_idx](attn_out[n_vlm:])     # mlp_dim=4096

    return vlm_out, act_out

为什么动作专家比 VLM 专家小那么多？

VLM 专家（width=2048, mlp_dim=16384）需要处理图像和语言这两个语义丰富的模态——它需要理解数十亿概念和它们之间的关系。而动作专家（width=1024, mlp_dim=4096）只需要学会一件事：在给定视觉和语言理解的前提下，生成正确的连续动作。这是一个相对"窄"的任务，不需要那么大的容量。

与 HyVLA 的 MoT 对比：π₀ 的"两个专家"本质上就是 MoT（Mixture-of-Transformers）的一种实现。HyVLA 把三个模态（视觉、语言、动作）各自分开了 QKV+FFN，而 π₀ 把视觉和语言合为一组（因为它们共用 PaliGemma 的预训练权重），只把动作分出去。核心思想完全一致：注意力共享，参数独立。

好处：直接加载 PaliGemma 预训练权重

因为 VLM 专家的 QKV 和 FFN 维度与原版 PaliGemma 完全一致，可以直接加载预训练好的 3B 权重，一个参数都不浪费。动作专家是从头随机初始化的——它不需要预训练，因为互联网上没有机器人动作数据，预训练也学不到有用的东西。

→ 衔接问题：两个专家通过联合注意力交互，但这个注意力不能让所有 token 随意互相看——否则动作 token 会"污染"VLM 的前向结果。下一节看 π₀ 怎么用块间因果掩码来精确控制信息流。
04

π₀ 的块间因果注意力掩码（✓ = 可以看到，✗ = 看不到）

三个设计决策的原因

为什么块 1（感知）看不到块 2、3？ 这是为了保护 VLM 预训练。PaliGemma 预训练时，从来没见过机器人状态或动作 token。如果让感知块看到这些"新模态"的 token，它的前向计算结果会和预训练时不同——相当于预训练权重被"污染"了。把感知块隔离开，它的输出和原版 PaliGemma 完全一致，预训练投资得到最大化利用。

为什么状态 qt 单独成块？ 因为机器人状态在 flow matching 的 10 步去噪过程中不会改变——当前时刻的关节角度是固定的。把它单独放一块，它的 KV 可以在 10 步去噪中全部缓存，不用重算。

为什么动作块内部是双向注意力？ 因为 flow matching 不是自回归生成——所有 H=50 个动作 token 是同时去噪的，每个动作 token 都需要看到其他动作 token 才能协调一致。如果是因果掩码（act₁ 看不到 act₂），前面的动作就无法考虑后面的动作，轨迹的全局一致性会变差。

# 块间因果掩码的构造
def build_block_causal_mask(n_perception, n_state, n_action):
    N = n_perception + n_state + n_action
    mask = zeros(N, N)  # 全 False

    p = n_perception
    s = n_state
    a = n_action

    # 块 1（感知）：只看块 1 内部（双向）
    mask[0:p, 0:p] = True

    # 块 2（状态）：看块 1 + 块 2（双向）
    mask[p:p+s, 0:p+s] = True

    # 块 3（动作）：看所有块（双向）
    mask[p+s:, 0:] = True

    return mask
→ 衔接问题：我们知道了动作 token 可以看到所有信息，但动作 token 一开始是什么？它是纯噪声，需要经过 flow matching 的去噪才能变成真实动作。下一节看这些噪声动作 token 是怎么嵌入到 Transformer 中的。
05

噪声动作嵌入与时间步编码——Flow Matching 的输入准备

动作 token 不是词表里的离散符号，而是连续向量。怎么把"噪声动作 + 去噪进度"编码成 Transformer 能理解的 token？

什么是"噪声动作"？

在 flow matching 中，我们不是直接预测最终动作，而是从纯噪声出发，一步步"去噪"得到真实动作。训练时，给定真实动作 At，我们加噪得到：

# 噪声动作的构造
A_t_noisy = tau * A_t + (1 - tau) * epsilon
# tau ∈ [0, 1] 是去噪进度
# epsilon ~ N(0, I) 是标准高斯噪声
# tau = 0 → 纯噪声
# tau = 1 → 纯真实动作

对于 H=50 步的动作块，真实动作 At = [at, at+1, ..., at+49]，每个 a 是一个连续向量（比如 14 维：6 个关节 + 夹爪 + ...）。加噪后得到 50 个噪声动作向量。

把噪声动作嵌入成 Transformer token

每个噪声动作 aτi 需要和去噪时间步 τ 一起编码成一个 token。π₀ 用一个 MLP 来做这件事：

# 噪声动作嵌入（Appendix B 的细节）
def embed_noisy_action(a_noisy_i, tau, action_dim, expert_width=1024):
    # 1. 时间步 τ 用正弦位置编码展开成高维向量
    tau_encoding = sinusoidal_encoding(tau)  # 标量 → 向量

    # 2. 把噪声动作和时间步编码拼在一起
    combined = concat(a_noisy_i, tau_encoding)  # [action_dim + tau_dim]

    # 3. 通过带 swish 激活的 MLP 映射到动作专家的维度
    #    公式：W3 · swish(W2 · concat(W1 · a_noisy_i, phi(tau)))
    h1 = W1 @ a_noisy_i         # [action_dim] → [2*width]
    h2 = phi(tau)                # 正弦编码
    h = swish(W2 @ concat(h1, h2))  # → [width]
    token = W3 @ h               # → [expert_width=1024]

    return token  # 这就是一个动作 token，可以送进 Transformer

# 每个时间步有 H=50 个动作 token
action_tokens = [embed_noisy_action(a_noisy[i], tau)
                 for i in range(H)]

为什么时间步 τ 这么重要？

Transformer 需要知道"当前去噪到了什么程度"，才能输出正确的速度场。如果 τ ≈ 0（几乎全是噪声），模型应该输出一个粗略的方向；如果 τ ≈ 1（接近真实动作），模型应该输出精细的微调。没有 τ 信息，模型就不知道自己该做粗调还是细调。

类比理解：想象你在画一幅画。τ = 0 时相当于一张白纸，你应该先画大轮廓（粗调）；τ = 0.9 时画面已经基本成型，你应该只画细节（细调）。如果不告诉画家"你现在画到什么程度了"，画家就会一直画粗笔触或一直画细节，无法配合。

状态 token 的嵌入

机器人本体状态 qt（一个连续向量，如 14 维关节角度）的嵌入更简单——不涉及时间步，只需要一个线性投影层把它从原始维度映射到动作专家的维度（1024）：

state_token = linear_projection(q_t)  # [14] → [1024]
→ 衔接问题：噪声动作 token 已经准备好了，送进 Transformer 和视觉语言 token 一起计算注意力后，怎么从输出中提取"速度场"来去噪？下一节看 Flow Matching 的完整生成过程。
06

Flow Matching 动作生成——从噪声到连续动作

Flow Matching 是 π₀ 输出动作的核心机制。它不预测"最终答案"，而是预测"当前应该往哪个方向走一步"。

为什么不用 MSE 直接回归动作？

在 HyVLA 指南里我们讲过这个问题：如果用 MSE loss 直接回归动作，当同一个场景有多种合理动作时（比如"左手抓"和"右手抓"），模型会预测两者的平均值——一个既不是左手也不是右手的"幽灵动作"。

Flow matching 避免了这个问题：它学习的是一个速度场 v(x, τ)，从噪声出发，沿着这个速度场"流动"到真实动作分布的一个采样点。不同的噪声起点会流向不同的模式（左手或右手），自然避免了模式平均。

训练：学习速度场

# Flow Matching 训练损失
def flow_matching_loss(model, images, lang, state, A_true):
    """
    A_true: 真实动作块 [H, action_dim]，H=50
    """
    # 1. 采样噪声
    epsilon = randn_like(A_true)  # [H, action_dim]

    # 2. 采样时间步 τ ~ Beta 分布（偏向低 τ）
    tau = sample_beta(alpha=(s-tau)/s, beta=1.5, s=0.999)
    # Beta 分布偏向低 τ（高噪声），因为低噪声时速度场接近恒等映射，
    # 模型只需要学"不动"，不需要额外训练

    # 3. 构造噪声动作
    A_noisy = tau * A_true + (1 - tau) * epsilon

    # 4. 模型预测速度场
    v_pred = model(images, lang, state, A_noisy, tau)

    # 5. 真实速度场 = 真实动作 - 噪声
    #    （线性插值路径的导数恒为 A_true - epsilon）
    v_target = A_true - epsilon

    # 6. 损失 = 预测速度场和真实速度场的 MSE
    loss = MSE(v_pred, v_target)
    return loss

为什么用 Beta 分布采样 τ 而不是均匀分布？

π₀ 发现，对于机器人动作预测任务，τ 的采样分布很重要。和图像生成不同（那里用均匀或 logit-normal 分布），机器人动作有一个特殊性质：给定观测 ot，动作分布的约束比给定文本标签的图像分布强得多。也就是说，在高 τ（低噪声）时，模型几乎不需要做什么——观测已经把动作锁定了。

所以 π₀ 用一个偏向低 τ 的 Beta 分布（论文中 s=0.999），让模型把训练资源集中在"高噪声→需要做大动作修正"的困难情况上。而且，超过阈值 s 的 τ 直接不采样——因为这些时间步太接近 τ=1，速度场几乎为零，训练它们是浪费。

Beta 分布偏向低 τ，让模型集中学习高噪声时的速度场

推理：10 步欧拉积分

# Flow Matching 推理（动作生成）
def generate_actions(model, images, lang, state):
    # 从纯噪声出发
    A = randn(H, action_dim)  # τ=0 时的初始噪声
    delta = 0.1               # 步长 = 1/10

    for step in range(10):    # 10 步积分
        tau = step * delta    # τ: 0.0, 0.1, 0.2, ..., 0.9

        # 模型预测当前位置的速度场
        v = model(images, lang, state, A, tau)

        # 欧拉积分：沿速度场走一步
        A = A + delta * v     # A^{τ+δ} = A^τ + δ · v_θ(A^τ, o_t)

    return A  # 10 步后 τ=1.0，得到去噪后的真实动作

为什么是 10 步？

这是精度和速度的权衡。每一步都需要一次完整的 Transformer 前向传播（虽然有 KV cache 加速，但动作 token 仍需重算）。10 步在 RTX 4090 上总共约 27ms，加上图像编码和其他开销，总推理时间约 73ms——满足 50Hz 控制频率的要求（20ms 一步 × 50步 = 1 秒的动作块，73ms 远小于 1 秒）。

→ 衔接问题：现在我们知道了单个机器人的完整推理流程。但 π₀ 的目标是一个通用模型——它要同时控制七种不同构型的机器人。不同机器人的动作维度都不一样，怎么办？

问题：动作维度不一样怎么办？

最大的构型（Mobile Fibocom）有 17 维动作（两只 6-DoF 手臂 + 2 个夹爪 + 底盘 3 维），而最小的（UR5e）只有 7 维。π₀ 的做法简单粗暴但有效：

# 跨构型的动作维度统一
def unify_action_dim(action, robot_type, max_dim=18):
    """
    所有机器人的动作都填充到 max_dim=18 维
    （18 = 最大构型的维度：2×6-DoF手臂 + 2夹爪 + 移动底盘 + 竖直扭矩）
    """
    # 原始动作（各构型维度不同）
    original_dim = len(action)  # 7, 8, 14, 16, 或 17

    # 零填充到最大维度
    padded_action = zeros(max_dim)
    padded_action[:original_dim] = action

    return padded_action

# 同样，配置向量（关节角度）也零填充到 18 维
def unify_config_dim(config, robot_type, max_dim=18):
    padded_config = zeros(max_dim)
    padded_config[:len(config)] = config
    return padded_config

类似地，不同构型的相机数量也不同（2 或 3 个）。如果某构型只有 2 个相机，第 3 个相机的 image slot 在注意力掩码中被mask 掉——对应位置的 token 不参与注意力计算。

数据不平衡怎么处理？

不同构型的数据量差异很大（Mobile Fibocom 的数据远多于 UR5e）。π₀ 用一个 n0.43 加权来平衡：

# 数据加权策略
def compute_sampling_weight(n_samples):
    """
    n: 某个 (task, robot) 组合的样本数
    权重 ∝ n^0.43
    比线性加权（n^1.0）大幅降权大数据集
    比均匀加权（n^0.0）仍然让大数据集多出现
    """
    return n_samples ** 0.43

这是一个常见的数据平衡策略：指数 0.43 是经验值，介于"完全均匀"（0.0）和"按比例"（1.0）之间。直觉上，大数据集已经足够多样了，不需要让它按原始比例出现；但也不能完全均匀，否则小数据集会被过拟合。

跨构型训练的好处：不同构型的数据可以互相帮助。比如"抓取杯子"这个技能，在 UR5e 上的抓取数据可以帮助 Franka 更快学会抓取——因为 VLM 专家学到的"杯子在哪里、该从哪个角度接近"这些语义知识是与构型无关的，它们通过共享的注意力机制传递给动作专家。

→ 衔接问题：我们有了统一的架构和跨构型的数据处理方式。但怎么训练这个模型？π₀ 借鉴了 LLM 的"预训练 + 后训练"范式。下一节看具体的训练策略。

预训练与后训练——类比 LLM 的训练范式

π₀ 的训练范式和 LLM 惊人地相似：先在大规模杂数据上预训练，再在高质量数据上后训练。

预训练阶段

预训练数据混合了两部分：

π 数据集（90.9%）——π₀ 团队自己采集的 903M 时间步灵巧操作数据，来自 7 种构型 × 68 种任务，共 22 台机器人。这些数据包含高频（高达 50Hz）的复杂灵巧操作，如叠衣服、收拾桌子、装袋子等。数据还附带了丰富的语言标注：任务名称（如 "fold shirt"）和细粒度的分段标注（如 "pick up sleeve", "fold left"），每段约 2 秒。

OXE 子集（9.1%）——Open X-Embodiment 的开源数据，包括 BridgeData v2 和 DROID。这些数据覆盖更广泛的场景和物体，但大多是低频（2-10Hz）、简单任务的数据。它的作用是增加多样性和鲁棒性。

后训练阶段

预训练出来的是一个"粗通百艺"的基础模型——它能跟随语言指令做很多任务，但在任何一个特定任务上都不算精通。后训练就是在特定任务的高质量数据上微调。

为什么两阶段比只用高质量数据好？ 论文的实验给出了清晰的答案：

只用高质量数据（scratch）——模型没见过多样化的场景和错误恢复，变得"脆弱"：一旦偏离训练分布就不知道怎么办。
只用预训练数据（out-of-box）——模型能力广泛但不精通，复杂任务（如叠衣服）成功率不够高。
预训练 + 后训练——两全其美：预训练提供了广泛的操作知识和错误恢复能力，后训练教会了流畅高效地完成特定任务。

一个直觉：预训练就像医学生的住院实习——大量接触各种病例，学会基本功和临场应变。后训练就像专科培训——集中训练特定手术的标准流程，追求精准和流畅。只做专科培训的医生遇到意外状况会慌，只做住院实习的医生做手术不够熟练。

High-Level VLM 策略

对于需要多步推理的复杂任务（如"收拾桌子"需要判断什么是垃圾、什么是碗筷），π₀ 还可以配合一个 High-Level VLM 策略：

# High-Level VLM 策略（用于多阶段任务）
def high_level_policy(images, task_description):
    """
    一个独立的大 VLM（不是 π₀ 自己），
    把高层任务分解成一系列子指令
    """
    # 类似 SayCan 的方法
    sub_commands = VLM.generate(
        f"Task: {task_description}\n"
        f"Given the current scene, what is the next step?\n"
        f"Be specific: mention the object and target location."
    )
    # 例如 "bus the table" →
    #   ["pick up the cup", "place it in the bin",
    #    "pick up the plate", "place it in the dish rack", ...]
    return sub_commands

# 执行：依次把每个子指令作为 π₀ 的语言输入
for cmd in sub_commands:
    while not is_done(cmd):
        actions = pi0.generate_actions(images, cmd, state)
        robot.execute(actions)

推理与部署——KV Cache 加速与动作块执行

10 步去噪 × 18 层 Transformer 的计算量不小，但 KV Cache 让推理时间压缩到了 73ms。

KV Cache 在 π₀ 推理中的作用

回忆 flow matching 推理：需要做 10 步去噪，每一步都是一次 Transformer 前向传播。但关键观察是：在这 10 步中，只有动作 token 在变化——图像、语言、状态都没有变。

# KV Cache 加速推理的原理
def pi0_inference_with_cache(images, lang, state):
    # ======= 第一步：只做一次的计算 =======
    # 编码图像（14ms）
    img_tokens = SigLIP(images)

    # VLM 前向 + 状态前向（32ms）
    # 计算感知块和状态块的 KV，并缓存
    K_perception, V_perception = vlm_expert.compute_KV(img_tokens, lang_tokens)
    K_state, V_state = action_expert.compute_KV(state_token)
    # 这些 KV 在接下来 10 步中不变，直接复用

    # ======= 10 步去噪：只重算动作 token =======
    A = randn(H, action_dim)  # 初始噪声

    for step in range(10):    # 总共 ~27ms（每步约 2.7ms）
        tau = step * 0.1

        # 嵌入当前噪声动作
        act_tokens = embed_noisy_actions(A, tau)

        # 只计算动作 token 的 Q，然后用缓存的 K/V 做注意力
        Q_act = action_expert.compute_Q(act_tokens)
        K_act, V_act = action_expert.compute_KV(act_tokens)

        # 动作的 Q 查询所有 K/V（包括缓存的感知和状态）
        K_all = concat(K_perception, K_state, K_act)  # 缓存 + 新算
        V_all = concat(V_perception, V_state, V_act)  # 缓存 + 新算
        attn_out = attention(Q_act, K_all, V_all)

        # FFN + 输出投影
        velocity = action_expert.ffn_and_head(attn_out)
        A = A + 0.1 * velocity

    return A  # 最终动作块

动作块的执行策略

每次推理生成 H=50 步的动作块，但不会等全部执行完才推理下一次。π₀ 采用了类似 HyVLA 的 Receding-Horizon（滚动时域）策略：

# 动作块执行策略
def receding_horizon_execution(pi0_model, robot):
    """
    不同频率的机器人，执行不同数量的动作后重新推理
    """
    while task_not_done:
        # 生成 H=50 步动作
        action_chunk = pi0_model.generate_actions(
            robot.get_images(),
            language_command,
            robot.get_state()
        )

        if robot.control_freq == 20:   # 20Hz: UR5e, Franka
            # 执行 16 个动作后重新推理（约 0.8 秒）
            for i in range(16):
                robot.execute(action_chunk[i])
                wait(1/20)  # 50ms

        elif robot.control_freq == 50:  # 50Hz: 双臂, 移动
            # 执行 25 个动作后重新推理（约 0.5 秒）
            for i in range(25):
                robot.execute(action_chunk[i])
                wait(1/50)  # 20ms

        # 丢弃剩余动作，用最新观测重新推理
        # → 形成闭环反馈，能纠正执行偏差

为什么不拼接动作块？

π₀ 论文提到他们尝试过 temporal ensembling（把相邻动作块重叠部分做加权平均），但发现效果不如简单的 open-loop 执行。原因可能是 flow matching 生成的动作块本身已经足够平滑连贯，额外的拼接平滑反而引入了延迟和模糊。这和 HyVLA 用 Bézier 曲线拼接形成了有趣的对比——不同的团队在这个问题上做了不同的选择。

π₀ 的完整推理管线总结

# π₀ 完整推理管线（从传感器数据到电机指令）
def pi0_full_pipeline():
    """
    一次完整的推理循环
    """
    # 1. 采集传感器数据
    images = [cam.capture() for cam in cameras]  # 2-3 张 RGB 图
    q_t = robot.get_joint_angles()               # 关节角度
    language = "fold the shirt"                   # 自然语言指令

    # 2. 图像编码（14ms，SigLIP ViT）
    img_tokens = []
    for img in images:
        tokens = SigLIP_encoder(img)              # 每张图 → ~256 tokens
        img_projected = linear_proj(tokens)       # 投影到 VLM 维度
        img_tokens.append(img_projected)

    # 3. 语言编码
    lang_tokens = gemma_tokenizer(language)

    # 4. 状态编码
    state_token = linear_proj_action(q_t)         # 投影到动作专家维度

    # 5. 感知+状态的 KV Cache（32ms，只做一次）
    kv_cache = transformer_forward_prefix(
        concat(img_tokens, lang_tokens, state_token)
    )

    # 6. Flow Matching 去噪（27ms，10 步）
    A = randn(50, action_dim)
    for step in range(10):
        tau = step * 0.1
        act_tokens = action_embedding_mlp(A, tau)
        velocity = transformer_forward_actions(act_tokens, kv_cache)
        A = A + 0.1 * velocity

    # 7. 输出投影（动作 token → 真实动作值）
    actions = output_projection(A)  # [50, action_dim]

    # 8. 执行前 16-25 步，然后重新推理
    return actions

π₀ 与 HyVLA 的整体对比：两者的核心思想高度一致——都是 VLM + 动作专家 + Flow Matching + 块间因果掩码。主要差异在于：π₀ 用 PaliGemma（3B），HyVLA 用 Hy-Embodied-0.5；π₀ 把视觉语言合成一个专家，HyVLA 用 MoT 三路分开；π₀ 强调跨构型训练和预训练/后训练范式，HyVLA 强调紧凑记忆编码器和异步推理拼接。它们是同一个 VLA 设计哲学的两种实现。
